\section{Overview}

\begin{frame}{1Password in 2015}
  \begin{itemize}
    \item A successful password manager from home users.
    \item Very strong reputation for privacy as well as security and usability.
      \note[item]{E.g., among the first (2012) to encrypt URLs and item titles and to use authenticated encryption (Encrypt-then-MAC).}
    \item Did not host customer data in any form.
    \item Hooks for users to sync their data using Dropbox and other third party solutions.
  \end{itemize}
\end{frame}

\begin{frame}{Why run a service?}
  We were increasingly hit by a number of problems, including:
  \begin{itemize}
    \item Maintaining sync mechanisms with different third party services was getting harder;
    \item Third party sync services didn't have all security requirements we wanted;
    \item Users could not reliably share subsets of their data with other members of families or teams.
  \end{itemize}
  Running our own service would require, among other things, building an authentication system for it.
\end{frame}

\section{Review}

\begin{frame}
  \frametitle{Background concepts}

  For what follows, we need a high level understanding of some of the differences between authentication and encryption as well as to how password cracking (whether for encryption or authentication) is possible.
\end{frame}

\subsection{Password managers are not based on authentication}

\begin{frame}{Penelope and Victor}

  Authentication involves a prover, $P$, and a verifier, $V$.
  $V$ has the power to grant $P$ access to some resource.

  \note[item]{I'm combining authorization and authentication}

  \begin{itemize}
    \item $P$ has access to a secret, $s$.
    \item $P$ proves to $V$ that she knows $s$, typically sending him $s$.
    \item $V$ verifies that $s$ is the correct secret for $P$
    \item If the check passes, $V$ grants $P$ access.
  \end{itemize}
\end{frame}

\begin{frame}{Spoils to the Victor}
  \begin{itemize}
    \item $V$ has the capacity to gran access even if a good proof is not provided.
    \item $V$ may not be the only entity with the capacity to grant access.
  \end{itemize}
\end{frame}

\begin{frame}{Decryption is transformative}
  \begin{itemize}
    \item Alice has a small secret, $s$, perhaps it is a password.
      \note[item]{$s$ is typically derived from a password.}
    \item Alice has two non-secret mathematical functions $E$ and $D$.
    \item $c = E(k, m)$, $m = D(k, c)$, and for all $m$ and $k$: $D(k, E(k, m)) = m$
  \end{itemize}
\end{frame}

\begin{frame}<beamer:0>{Decryption requiers the secret}
  \begin{itemize}
    \item The function $D$ is not capable of producing $m$ from $c$ without $k$.
    \item There is no other function that is feasibly capable of producing $m$ from $c$
      \note[item]{Well, I should speciffy that these functions also don't have access to $m$.}
  \end{itemize}

\end{frame}

\begin{frame}{Passwords for all reasons}
  \begin{table}
    \begin{tabular}{lP{0.25\textwidth}P{0.25\textwidth}P{0.25\textwidth}}
      & Meatspace
      & Authentication
      & Decryption \\
      \midrule
      Password
      & Something you know that is said to a to prove you are authorized to enter
      & Secret told to system to prove you are authorized to do stuff
      & Converted to a key necessary to transform data.

    \end{tabular}
  \end{table}
\end{frame}

\subsection{Cracking}
\begin{frame}
  \frametitle{Cracking authentication}
  Verifiers store something, typically a hash of the password,
  which if captured by an attacker can be used to for password cracking
\end{frame}

\begin{frame}
  \frametitle{Cracking (decryption)}

  Decryption keys are typically derived from password using a key derivation function (KDF) which will including hashing.
\end{frame}

\begin{frame}
  \frametitle{Can hashes be reversed?}

  Cryptographic hash functions are (hopefully) pre-image resistant, meaning
  that given $h$ and a hash function $H$ it is effectively impossible to compute
  the $m$ of $h=H(m)$\uncover<1>{.}\uncover<2>{\alert{if $m$ is chosen uniformly from a large space.}}
\end{frame}

\begin{frame}
  \frametitle{Human created passwords are crackable}
  \note[item]{This, of course, is why password managers are necessary,
  but we will be taking amount the password needed to unlock the password manager.}
  \begin{itemize}
    \item Humans can't create high entropy passwords;
      \note[item]{My lame claim to fame is having written a
        \href{https://1password.com/blog/toward-better-master-passwords}{2011 blog post}
        (since revised) that inspired the
      \href{https://xkcd.com/936/}{XKCD “correct horse battery staple” comic.}}
    \item Humans can't remember more than a few medium entropy passwords.
      \note[item]{Joseph Bonneau and Stuart Schechter were able to train people on 56-bit passwords, but it required learning the password incrementally. See \url{https://www.usenix.org/conference/usenixsecurity14/technical-sessions/presentation/bonneau
      }}
  \end{itemize}

    \caption{“I'm So Random”: \href{https://xkcd.com/1210}{xkcd 1210}}

\end{frame}

\section{Specific authentication concerns}

\begin{frame}
  \frametitle{Specific concerns}
  \begin{itemize}
    \item Server must not receive decryption secrets during authentication;
      \note[item]{Every password manager with an authentication process must address this problem.}
    \item Remain secure even if TLS fails;
      \note[item]{TLS was in bad shape at the time. It has dramatically improved since then.}
    \item Service does not hold onto anything that is crackable.
      \note[item]{The crackability problem is not really about authentication, though it does interact with it. And it would be a separate talk on its own. See \href{https://1password.com/blog/what-the-secret-key-does}{“Secret Key: What is it, and how does it protect you?”} for disucssion of that.}
  \end{itemize}

\end{frame}

\begin{frame}
  \frametitle{Don't receive decryption secret}
  In a traditional authentication mechanism, the user password is transmitted
  to the server, the verifier hashes it, discards the password, and compares the hash to stored hash. Relying on the verification process to discard the secret it receives does not meet the security requirements for a password
  manager.

  Possible solutions
  \begin{enumerate}
    \item Separate password for authentication and decryption
      \note[item]{Separate authentication password is a tough sell for a product named 1Password.}
    \item Pre-hashing password before transmitting
      \note[item]{Prehashing alone may make things harder for a malicious server to recover decryption password, but we'd like to do better.}
    \item Password-authenticated key exchange (PAKE)
      \note[item]{The bulk of this talk is about implementing a PAKE in 2015.
      A PAKE also remains secure if TLS fails.}
  \end{enumerate}
\end{frame}

\section{General authentication desiderata}

\begin{frame}
  \frametitle{Mutual authentication}
  We not only want the client to prove its identity to the server, but we also
  want the server to prove its identity to the client.

  \begin{description}
    \item[CI] \propdescription{Proof of client identity}
    \item[SI] \propdescription{Proof of server identity}
      This is typically handled by TLS, but we wanted the system to retain its security properties if even if TLS fails. Confidence in TLS has (correctly) improved since 2015.
  \end{description}
\end{frame}

\begin{frame}
  \frametitle{No secrets transmitted, no replay, no tampering}
  \begin{description}
    \item[NS] \propdescription{No secrets received}
      Traditional password authentication emphatically fails to meet this.
    \item[NR] \propdescription{No replay}
      An eavesdropper can't learn anything that would allow them to successfully replay an authentication session;
    \item[NT] \propdescription{No tampering}
      An active attacker who can tamper with the communication can only prevent successful authentication but cannot learn any secrets.
  \end{description}
  \note[item]{Previously I erronousely refered to NS as “Zero knowledge”. That misuse of the term seems to have caught on. Sorry.}

  I will refer to the set of these as “NS+”.
\end{frame}

\begin{frame}
  \frametitle{Key Exchange}
  \begin{description}
    \item[KE] \propdescription{Key exchange}
      The authentication process results in both sides knowing an encryption key for the session. Proper use of that session key for all communication during the session provides a strong proof that each message comes from a party that successfully went through the authentication process.
      \note[item]{Proper use means that each message is authenticated (through AEAD or a MAC with a key derived from the session key.)}
  \end{description}
\end{frame}

\begin{frame}
  \frametitle{Only the above}
  There are more slides in this section talking about other desirable properties of an authentication system, but now we will skip ahead to the first slide of the next section,
  \nameref{sec:pake}.
  \note[item]{I am really tempted to spend time on fixing this cross reference, but I should work on content instead.}
\end{frame}

\begin{frame}
  \frametitle{Properties of long term secret}
  \begin{description}
    \item[BigH] \propdescription{High entropy}
      TOTP is an example of this.
    \item[Uniq] \propdescription{Unique long term secrets}
      If an attacker obtains the a client secret used for one service,
      it gives them no information about any other authentication secret.
      Password reuse fails at this.
    \item[NoCrk] \propdescription{Uncrackable server verifiers}
      Protects users if server gets breached. Reduces incentives to breach the service.
  \end{description}
\end{frame}

\begin{frame}{Usable}
  \begin{description}
    \item[Use] \propdescription{Reliably and securely usable}
      People need to be able to use the system, and the system should be designed to make it easy for people to do things in their own privacy and security interests while hard to do things that go against those interests.
      \note[item]{This is much harder than one might imagine. For example, most users are not going to distinguish between a password used for authentication versus one for decryption, yet the semantics of a password change for can be catestrophically different.}
  \end{description}

\end{frame}

\begin{frame}
  \frametitle{Undesirable desiderata}
  \note[item]{Oxymoronic slide title.}
  There are features that may be desirable for systems
  that may need to avoided or created with strong restrictions
  for a password manager.
  \begin{description}
    \item[Reset] \propdescription{Recoverability}
      Any entity that has the power to reset a forgotten or lost authentication secret has the capability to to take over the account.
      \note[item]{1Password's recovery mechanism is nightmarishly complicated,
      and would be a topic for another day.}
    \item[Alt] \propdescription{Alternative authentication}
      Sometimes what is labeled as two-factor authentication is better described as alternative factor authentication.
      This is extremely dangerous if users are led to believe that it
      helps keep attackers out.
  \end{description}
\end{frame}

\begin{frame}
  \frametitle{Distinct factors}
  \begin{description}
    \item[MF] \propdescription{Multiple factor}
      If at least one of multiple authentication factors is not compromised, the authentication process retains its security properties.
      \note[item]{This is widely and often dangerously misunderstood. And is a separate topic.}
  \end{description}
\end{frame}

\section{Password-Authenticated Key Exchange (PAKE)}\label{sec:pake}
\begin{frame}
  \frametitle{What a PAKE does}
  \label{frame:pake}
  A well designed password authenticated key exchange (PAKE) protocol gives us
  the following security authentication security properties
  \begin{description}
    \item[CI] Proof of client identity
    \item[SI] Proof of server identity
    \item[NS] No secrets received
    \item[NR] No replay
    \item[NT] No tampering
    \item[KE] Key exchange
  \end{description}
\end{frame}

\begin{frame}
  \frametitle{Enrollment}
  \begin{enumerate}
    \item Generate long term client secret, $x$, from password, salt ($s$), etc
      \note[item]{For the PAKE we ended up using the long term client secret is called $x$, so we are stuck with that.}
    \item Compute a mathematically related verifier, $v$.
      \note[item]{I am describing an augmented PAKE, in which it is infeasible to compute $x$ from $v$.}
    \item Send $v$ and $s$ to service.
      \note[item]{Sending $v$ to the service is the only time a secret is transmitted}.
  \end{enumerate}
\end{frame}

\begin{frame}
  \frametitle{Authentication: Compute shared $K$}
  \begin{enumerate}
    \item Client generates an ephemeral client secret, $a$.
    \item Client generates an ephemeral public key, $A$, from $x$ and $a$.
    \item Client sends $A$ (along with identity, $I$) to server.
      \note[item]{Identity is something like username.}
    \item Server generates an ephemeral server secret, $b$.
    \item Server generates an ephemeral public key, $B$, from $v$ and $b$.
    \item Server sends $B$ to client.
    \item Client computes $K_c$ from $x$, $a$, and $B$.
    \item Server computes $K_a$ from $v$, $b$, and $A$.
  \end{enumerate}
  If $x$ and $v$ have the right mathematical relation, then $K_s = K_c$.

  \note[item]{The computations, sequence of computaton, nature of public parameters used, and even the number of messages back and forth depend on the particular PAKE.}

\end{frame}

\begin{frame}
  \frametitle{Authentication: Check shared $K$}
  $K_s = K_c$ only if $x$ and $v$ have the right mathematical relation.

  \begin{block}{Notation}
    \begin{small}
      \begin{itemize}
        \item “$\xor$” is exclusive or; “$|$” is reversible concatenation;
        \item $H$, an agreed upon cryptographic hash function;
        \item $g$, a public parameter used computations;
        \item $s$, the salt, shared during enrollment;
        \item $I$, the client's identify, set during enrollment;
        \item $K_c$ and $K_s$, keys that the client (C) and server (S) have computed.
      \end{itemize}
    \end{small}
  \end{block}
  \begin{enumerate}
    \item C sends  $M_1 = H(H(N) \xor H(g)\| H(I) | s | A | B | K_c)$ to S.
    \item S verifies $M_1$.
    \item S sends $M_2 = H(A | M_1 | K_s)$ to C.
    \item C verifies $M_2$.
  \end{enumerate}
  \note[item]{Details don't matter (and there are different ways to do this.) What matters is that there is a way for the client and the server to each prove to each other that they have the same $K$ without revealing any secrets.}
\end{frame}

\begin{frame}
  \frametitle{Choosing a PAKE: Criteria}
  \begin{itemize}
    \item Existing libraries we could use;
    \item Augmented PAKE ($x \neq v$)
      \note[item]{The reason for seeking an augmented PAKE is so capture of the server stored verifier $v$ could not lead to impersonation of a client.}
    \item Clear of any patents.
      \note[item]{At the time were were some contestable patents on categories of PAKEs, and I lived in the Eastern Federal Distict of Texas.}
  \end{itemize}
\end{frame}

\begin{frame}
  \frametitle{Existing libraries: Nothing for all our platforms}
  Our clients included things written in Objective-C (Mac and iOS), Delphi (Windows), Java (Android), and our planned web-clients that needed to run in Safari, Edge, Firefox, and Chrome.
\end{frame}

\begin{frame}
  \frametitle{Existing libraries: Linking}

  \begin{inprinciple}
    A single portable library written in C could be linked to our native clients.
  \end{inprinciple}

  \begin{inpractice}
    Our experience doing that with OpenSSL had been unpleasant
    More importantly, this wasn't going to work with web-clients.
  \end{inpractice}
\end{frame}

\begin{frame}
  \frametitle{Web-clients}

  \begin{inprinciple}
    In principle web-clients should not have been a thing, not only did they severely limit what sorts of cryptographic libraries we could use, but given the way the client is delivered their security did depend on TLS.
  \end{inprinciple}

  \begin{inpractice}
    Web-clients were absolutely necessary, as features (particularly administrative ones) could be developed and deployed quickly to all customers. Adding new UI to native clients was much slower, and releasing
    an updated native client was subject to additional delays, including app store processes.
  \end{inpractice}

\end{frame}

\begin{frame}
  \frametitle{Underlying group}
  \alert{Do not roll your own cryptographic implementations!}

  \begin{inprinciple}
    We should use elliptic curves for the underlying group.
  \end{inprinciple}

  \begin{inpractice}
    The libraries available to us did not expose elliptic curve primitives, but anything with a big integer library could perform the computations for integer fields.
  \end{inpractice}

\end{frame}

\begin{frame}{Timing attacks}

  \begin{inprinciple}
    We should ensure that our implementation defends against timing and other
    side-channel attacks.
  \end{inprinciple}

  \begin{inpractice}
    We did not have access to big integer libraries that did so, and we didn't have the highly specialized skills to do that generally.
    We did defend against the ones that we easily could.
  \end{inpractice}
\end{frame}

\section{Lessons from rolling our own}

\begin{frame}
  \frametitle{Developers need guidance}
  Pointing even very talented developers at a standard and expecting them
  to implement well if they don't understand why the protocol works leads to problems
  \note[item]{I failed to provide enough guidance during development.}
  \begin{itemize}
    \item Without an understanding of how the pieces fit together, code can be wildly misfactored.
      \note[item]{Poor code organization contributed to my failure to notice that an important check was not being performed. Bounty hunter found during testing that check that client ephemeral public, $A$ was not being checked for $A  \not\equiv 0 \pmod N$.}
    \item Developers didn't know which parts of computation where cryptographic secrets.
      \note[item]{Most anyone who has had some course in cryptography will be familiar with the convention during key exchange that little $a$ is an ephemeral client secret and big $A$ is an ephemeral public key. But most developers won't know that. Only after seeing little $a$ not properly handled did I change our variable name to \texttt{ephemeralClientSecret}.}
    \item Allowed a seemingly harmless shortcut in not padding a number before hashing that lead to a Heisenbug years later.
  \end{itemize}

\end{frame}

\begin{frame}{Progress}
  In the years that followed, a common core library for all clients was developed in Rust. That was an intensive, multi-year project. 
  
  Additionally greater cryptographic expertise was brought on board.
\end{frame}
